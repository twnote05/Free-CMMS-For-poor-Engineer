# โจทย์: ขอไอเดียปรับปรุงระบบ Stock อะไหล่ — โรงงานพื้นไม้คอมโพสิต

> ก๊อปทั้งไฟล์นี้วางให้ AI ตัวไหนก็ได้ (ChatGPT / Gemini / Claude ตัวอื่น / ที่ปรึกษาที่เป็นคน)
> ตั้งใจให้อ่านจบแล้วให้ฟีดแบ็กได้ทันทีโดยไม่ต้องเห็นซอร์สโค้ด

---

## บทบาทของคุณ

คุณคือที่ปรึกษาที่เคยวางระบบคลังอะไหล่ในโรงงานมาก่อน และเคยเห็นระบบที่
ตัวเลขสวยในจอแต่ของบนชั้นไม่ตรง คุณจึงเกลียดฟีเจอร์ที่ "ดูดีตอนเดโมแต่ไม่มีใครกรอก"
พอ ๆ กับที่เกลียดระบบที่ยอดคงเหลือเชื่อไม่ได้

อ่านบริบทข้างล่างให้จบ แล้วให้ **ไอเดียปรับปรุงที่ลงมือได้จริง** ไม่ใช่รายการ best practice
ทั่วไป ถ้าข้อไหนผมทำไปแล้วหรือชนข้อจำกัด บอกมาตรง ๆ ว่าข้ามได้

# 1. บริบทธุรกิจ

โรงงานผลิตแผ่นพื้นไม้เทียม / แผ่นพลาสติก มีเครื่องจักรหลัก ~22 ตัว
(สาย Hotmix, Cooltmix, Extruder, UV, Multiblade, Slot, Mold, ปั๊มลม, Utility)

**แผนกซ่อมบำรุงดูแลคลังอะไหล่เอง** ไม่มีแผนกจัดซื้อหรือสโตร์แยก
คนเบิกกับคนจ่ายของคือคนเดียวกัน — ช่างเดินไปหยิบของจากชั้นเอง

ของในคลังมีสามกลุ่ม:
- **อะไหล่** 997 รายการ — ลูกปืน ซีล มอเตอร์ อินเวอร์เตอร์ โซลินอยด์ ฮีตเตอร์ สายพาน
- **เครื่องมือช่าง** 94 รายการ — ประแจ บล็อก ไขควง แยกตามทีม 5 ทีม ว่าอยู่กับใคร
- **ใบมีด** 145 ใบ — ของสิ้นเปลืองที่มีวงจรชีวิต: ติดตั้ง → ใช้งาน → ส่งลับคม → กลับมาใช้ → ปลดระวาง

**ปริมาณงานจริง:** การเบิกไม่กี่สิบครั้งต่อสัปดาห์ ไม่ใช่หลักพัน
ระบบนี้**ไม่ได้มีปัญหาเรื่อง scale** ปัญหาคือความถูกต้องและการที่คนจะใช้จริงหรือไม่

# 2. ข้อจำกัดที่ห้ามแตะ (ไอเดียไหนชนข้อนี้ ไม่ต้องเสนอ)

1. **Google Apps Script + Google Sheets เท่านั้น** — โรงงานไม่มีงบเซิร์ฟเวอร์
   และไม่มีคนดูแลถ้าผมออก · ห้ามเสนอให้ย้ายไป SQL / Firebase / CMMS สำเร็จรูป
2. **ไม่มีแอดมินคอยมอนิเตอร์** — ผู้ใช้มีแค่ระดับปฏิบัติการสามชั้น
   ช่าง → หัวหน้าช่าง → วิศวกรปฏิบัติการ · ทุกอย่างต้องอธิบายตัวเองได้
3. **ช่างใช้มือถือ Android ราคาถูก เน็ตโรงงานช้า** บางจุดสัญญาณไม่ถึง
4. **เวลาฝึกต่อคนไม่เกิน 5 นาที** ถ้าต้องอบรมนานกว่านี้ถือว่าออกแบบพลาด
5. **ช่างยืมมือถือกันใช้ และหลายคนไม่มีบัญชี Google ของบริษัท**
   → ใช้ PIN ไม่ใช่ Google OAuth เป็นการตัดสินใจตั้งต้น ไม่ใช่ความขี้เกียจ
6. **ข้อความทั้งระบบเป็นภาษาไทย** ฝังในโค้ด ไม่ได้แยกไฟล์ภาษา
7. ระบบ CMMS แจ้งซ่อมเป็นคนละโปรเจค (ทีมเดียวกัน) **ยังไม่ได้เชื่อมกัน**

# 3. สถาปัตยกรรม

## กฎข้อเดียวที่ทำให้ทุกอย่างถูก

> **ยอดคงเหลือไม่เคยถูกเก็บเป็นคอลัมน์ มันคือ `SUM(Qty_Left)` ของ batch ทุกแถวของอะไหล่ตัวนั้น**

ทุกพฤติกรรมที่ถูกต้องงอกจากการตัดสินใจข้อนี้: FIFO เป็นของจริงเพราะ batch เป็นแถวจริง ·
ต้นทุนผูกกับ batch ไม่ใช่ค่าเฉลี่ย · การคืนของคืนเข้า batch เดิมที่เบิกออกไป ·
การนับสต๊อกปรับที่ batch ไม่ใช่เขียนทับตัวเลข · **ไม่มีช่อง "คงเหลือ" ให้เพี้ยนเงียบ ๆ**

สามแท็บแรกคือหน้างาน ที่เหลือซ่อนใต้ปุ่ม "หลังบ้าน"

## บทบาท

```js
const RANK = { TECH: 1, LEAD: 2, ENG: 3 };
```

บังคับที่ฝั่งเซิร์ฟเวอร์ด้วย `requireRole_(min)` ทุกฟังก์ชันที่เขียนข้อมูล
**การซ่อนปุ่มบนหน้าจอไม่ถือเป็นการคุมสิทธิ์** และไม่เคยถูกใช้แทน

**การปิดบังต้นทุนทำที่เซิร์ฟเวอร์** — `maskCost_()` เซ็ต `cost` กับ `value` เป็น 0
ก่อนส่งออก เมื่อผู้เรียกต่ำกว่าหัวหน้าช่าง · ตัวเลขที่ไม่ได้ส่งออกไป อ่านจาก DevTools ไม่ได้

## การยืนยันตัวตน

| | |
|---|---|
| เก็บ PIN | SHA-256 ของ `salt + pin` เทียบแบบ constant-time |
| อายุ session | 12 ชม. (หนึ่งกะ) |
| ใส่ผิด | 5 ครั้ง ล็อก 15 นาที |
| ทางออกฉุกเฉิน | `emergencyResetPin()` รันจาก editor เท่านั้น **จงใจไม่ใส่ใน allowlist** |

## ประตู API เดียว

```js
call(token, fnName, args)
```

`fnName` ต้องอยู่ใน allowlist **41 ตัว** ใน `Auth.gs` นอกนั้นโยน error
มีแค่ `login` กับ `logout` ที่เป็น public · ฟังก์ชันภายในลงท้ายด้วย `_` เรียกจากเบราว์เซอร์ไม่ได้โดยโครงสร้าง

## การกันคีย์ซ้ำ

ทุกการเขียนที่สร้างเอกสารรับ `ref` ที่เบราว์เซอร์สร้าง เซิร์ฟเวอร์จำ ref ที่สำเร็จไว้ใน
`CacheService` 6 ชั่วโมง · ส่ง ref เดิมมาอีก = คืนเลขเอกสารเดิม **ไม่เขียนอะไรเพิ่ม**

รูที่ปิด: ผู้ใช้กดยืนยัน → เน็ตหลุดตอนเซิร์ฟเวอร์ตอบ → ผู้ใช้กดใหม่
(ปุ่มถูกล็อกระหว่างรออยู่แล้ว ความเสี่ยงคือคำตอบหาย ไม่ใช่การกดรัว)

## Lock

ทุกฟังก์ชันที่เขียนครอบด้วย `lock_()` ซึ่งล้าง catalog cache ทั้งตอนเข้าและตอนออก
cache TTL 300 วินาทีเป็นแค่ตาข่ายกันพลาดกรณีมีคนพิมพ์ลงชีตตรง ๆ **ไม่ใช่กลไกหลัก**

# 4. สิ่งที่ทำเสร็จแล้ว (ไม่ต้องเสนอซ้ำ)

- **FIFO จริง** แบบ FEFO ก่อน FIFO — ของใกล้หมดอายุออกก่อน แล้วค่อยเรียงตามวันรับเข้า
  ตรวจทั้งยอดก่อนเขียนอะไรลงชีต
- **บัตรสต๊อก** ย้อนดูได้ทุกรายการ พร้อมเช็คว่ายอดตามบัตรตรงกับผลรวม batch จริงไหม
- **ระบบออกรหัสอะไหล่ 17 หลัก** ตามมาตรฐานเดิมของบริษัท (Code SP V1)
  73 หมวด · เพิ่มหมวดใหม่ได้จากหน้าจอ · **กันรหัสซ้ำสามชั้น**
- **เตือนถึงจุดสั่งซื้อ + สร้างใบสั่งซื้ออัตโนมัติ** จากของที่ต่ำกว่า Min
- **นับสต๊อก** ปรับส่วนต่างโดยตัดจาก batch เก่าสุด / สร้าง batch ใหม่ถ้าเกิน
- **คืนของ** เข้า batch เดิมที่เบิกออกไป
- **ตัดจำหน่าย** พร้อมเหตุผลบังคับทุกบรรทัด
- **ทะเบียนเครื่องมือช่าง** แยก 5 ทีม รู้ว่าอะไรอยู่กับใคร
- **วงจรชีวิตใบมีด** 145 ใบ แยก 4 เครื่อง — อายุใช้งานคำนวณจากวันติดตั้ง ไม่ให้คนกรอกเอง
- **พิมพ์แท็กบาร์โค้ด/QR** ติดหน้าช่องเก็บ (Code128 + QR, ขนาดกระดาษเป็น mm)
- **สแกนด้วยกล้องมือถือ** ทั้งหน้าเบิก นับสต๊อก ตัดจำหน่าย รับเข้า
  มีสองโหมดสลับอัตโนมัติ (กล้องสด / ถ่ายทีละใบ) เพราะ iframe ของ Apps Script บล็อกกล้องสดบางเครื่อง
- **รูปอะไหล่** ถ่ายจากมือถือเข้าระบบ หรือผูกทีเดียวทั้งคลังจากโฟลเดอร์ Drive ตามชื่อไฟล์
- **เตือนพื้นที่ใกล้เต็ม** + สำรองเป็น CSV แล้วตัดข้อมูลเก่า (เขียนไฟล์สำเร็จก่อนจึงลบ)
- **อีเมลสรุปประจำวัน** ของใกล้หมด ของหมดอายุ รหัสซ้ำ พื้นที่เก็บ
- **Audit log** ระดับฟิลด์ ว่าใครแก้อะไรจากค่าอะไรเป็นค่าอะไร
- **ชุดทดสอบ 5 ชุด** รันในหน่วยความจำ ไม่แตะชีตจริง (`node tests/run.js`)
- **ข้อมูลตั้งต้นฝังในโค้ด** รัน `setup()` ครั้งเดียวได้ของครบทั้งคลัง

# 5. จุดที่ผมเองยังไม่สบายใจ (อยากให้จิ้มแรง ๆ)

1. **ต้นทุนว่างทั้ง 997 รายการ** ชีตเดิมไม่เคยมีคอลัมน์นี้
   มูลค่าสต๊อกจึงเป็น ฿0.00 → รายงานมูลค่า การวิเคราะห์ ABC ของนอน **ใช้ไม่ได้เลยตอนนี้**
   จะไล่เก็บต้นทุนย้อนหลัง 997 รายการ หรือปล่อยให้ค่อย ๆ เติมตอนรับของเข้า?

2. **เกณฑ์เตือนถึงจุดสั่งซื้อคือ `คงเหลือ ≤ Min`** ของส่วนใหญ่ตั้ง Min = 1 และมีอยู่ 1 ชิ้นพอดี
   ผลคือเตือน 778 จาก 997 รายการ = **ไม่มีใครอ่าน**
   ถ้าเปลี่ยนเป็น `<` จะเหลือ 314 ซึ่งยังเยอะอยู่ดี
   ควรคิดใหม่ทั้งแนวคิดไหม (lead time? ความถี่การเบิก? Level A/B/C ที่มีอยู่แล้ว?)

3. **ยอดยกมาเป็นของวันที่ export ชีตเดิม ไม่ใช่ของวันนี้** 570 รายการ 6,257 ชิ้น
   ยังไม่ได้นับของจริง → ตัวเลขวันแรกอาจผิดตั้งแต่ต้น ซึ่งเป็นวิธีที่เร็วที่สุด
   ที่จะทำให้ไม่มีใครเชื่อระบบอีกเลย จะจัดการยังไงให้เจ็บน้อยสุด?

4. **ไม่มีอะไรบังคับให้ช่างเบิกผ่านระบบ** ถ้าเดินไปหยิบของจากชั้นเฉย ๆ ระบบไม่มีทางรู้
   ของจริงจะเพี้ยนจากระบบเรื่อย ๆ จนกว่าจะนับรอบหน้า — **นี่คือความเสี่ยงอันดับหนึ่ง
   และเป็นปัญหาคน ไม่ใช่ปัญหาโค้ด** มีวิธีออกแบบให้การเบิกผ่านระบบง่ายกว่าการไม่เบิกไหม?

5. **อายุใบมีดนับเป็นวันปฏิทิน ไม่ใช่ชั่วโมงเดินเครื่อง** เพราะข้อมูลเดิมเก็บมาแบบนั้น
   ใบมีดที่อยู่บนเครื่องที่หยุด 3 วัน กับเครื่องที่เดิน 24 ชม. นับเท่ากัน — ผิดชัด ๆ
   มีโปรเจคสถานะเครื่องจักรอยู่แล้ว ควรเชื่อมไหม หรือ over-engineering?

6. **22 รายการที่ชีตเดิมใช้รหัสเดียวกันกับของคนละชิ้น** เช่น รหัสเดียวเป็นทั้ง
   ข้อต่อลม 12 มิล และ 10 มิล · ระบบเก็บได้ตัวเดียวต่อรหัส อีกตัวตกค้างอยู่ในไฟล์รอคนตัดสิน

7. **`Data.gs` 387 KB ฝังข้อมูลไว้ในโค้ด** ใช้ตอนติดตั้งครั้งแรกเท่านั้น
   แต่มันอยู่ในโปรเจคตลอดไป ควรเอาออกหลังติดตั้งเสร็จไหม?

8. **ไม่มี git** ย้อนกลับได้ทางเดียวคือเวอร์ชันบน Apps Script

### A. ความถูกต้องของตัวเลขสต๊อก
ทำยังไงให้ยอดในระบบตรงกับของบนชั้นโดยไม่ต้องนับทุกเดือน

### B. ทำให้คนใช้จริง
ข้อ 5.4 คือปัญหาที่ใหญ่กว่าโค้ดทั้งหมดรวมกัน — มีแบบแผนที่ได้ผลจริงในโรงงานไหม

### C. เกณฑ์เตือนและการสั่งซื้อ
ข้อ 5.2 เตือน 778 จาก 997 = ไม่มีใครอ่าน ควรคิดใหม่ยังไง

### D. ต้นทุนและมูลค่า
ข้อ 5.1 ไม่มีต้นทุนเลย คุ้มไหมที่จะไล่เก็บย้อนหลัง หรือมีทางอื่น

### E. สถาปัตยกรรมและขีดจำกัด Apps Script
มีอะไรจะพังตอนข้อมูลโต 3 ปี · ของที่ผมมองไม่เห็น

### F. คุณค่าที่ยังไม่ได้เก็บเกี่ยว
ข้อมูลที่มีอยู่แล้วแต่ยังไม่ได้ใช้ · ควรต่อกับ CMMS ตอนไหน

### G. การส่งต่อ
ถ้าผมออกพรุ่งนี้ อะไรจะพังก่อน

### H. สามอย่างที่ควรทำก่อน
เรียงตามความคุ้มค่าต่อเวลาที่ใช้ พร้อมประมาณการชั่วโมง

### I. สิ่งที่คุณคิดว่าผมทำเกินจำเป็น
ฟีเจอร์ไหนควรถอดทิ้งหรือหยุดพัฒนาต่อ — **ข้อนี้อยากได้จริง ๆ ไม่ได้ถามเอาใจ**

---

## กติกาของคำตอบ

1. **ทุกข้อต้องบอกเวลาโดยประมาณ** (ชั่วโมง/วัน) ไม่งั้นเอาไปจัดลำดับไม่ได้
2. **บอกด้วยว่าข้อไหนขึ้นกับข้อไหน** อะไรต้องทำก่อน
3. **ถ้าข้อไหนชนข้อจำกัดในหมวด 2 ไม่ต้องเสนอ** หรือถ้าคิดว่าข้อจำกัดนั้นผิด
   ให้เถียงมาตรง ๆ พร้อมเหตุผล
4. **ของที่ทำเสร็จแล้วในหมวด 4 ไม่ต้องเสนอซ้ำ** ถ้าคิดว่าที่ทำไปยังไม่พอ บอกว่าขาดตรงไหน
5. **อย่าเสนอให้เขียนใหม่ทั้งระบบ** ระบบนี้ใช้ได้แล้ว ต้องการการปรับปรุง ไม่ใช่การรื้อ
6. ถ้าต้องเดาเพราะข้อมูลไม่พอ **บอกว่ากำลังเดา** และบอกว่าอยากรู้อะไรเพิ่ม
